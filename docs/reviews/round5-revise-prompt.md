### 確定方針（ラウンド5）

1. **G01 原子性 — SQL error barrier を採用（R4 方針を撤回）**: D1 batch 内で「必須条件の不成立を SQL error にする」ために `_assert` テーブル方式を採用:
   ```sql
   CREATE TABLE _assert (v INTEGER NOT NULL CHECK (v = 0));
   -- 各必須 step の直後に:
   INSERT INTO _assert(v) SELECT 1 WHERE changes() <> 1;           -- 影響行 assertion
   -- 事前条件 assertion（例）:
   INSERT INTO _assert(v) SELECT 1 WHERE NOT EXISTS (
     SELECT 1 FROM nodes WHERE id = ?1 AND revision = ?2 AND deleted_at IS NULL);
   ```
   CHECK 違反は SQL error なので batch 全体が rollback される（D1 公式: batch は暗黙 transaction、いずれかの statement がエラーなら全体 rollback）。`changes()` が D1 batch 内で直前 statement を指すことは **Phase 0 の gate 1** で実証し、失敗時は EXISTS 型 assertion のみで組む fallback を明記。`meta.changes` の JS 検査は二次診断に限定。R5 G01 の 3 反例（node revision 不一致 / tree generation 不一致 / trash root revision 不一致）を §15 の regression fixture として明記。
2. **G02 fence**: D1 に `permits(permit_id PK, space_id, epoch, expires_at, state IN ('open','released','revoked'))` を置き、LockDO は permit 発行時にまず D1 へ `open` を INSERT してから Worker に返す。全 mutation batch は `INSERT INTO _assert SELECT 1 WHERE NOT EXISTS (SELECT 1 FROM permits WHERE permit_id=? AND state='open' AND epoch=(SELECT epoch FROM control))` を含む。期限切れ回収: LockDO は `UPDATE permits SET state='revoked' WHERE permit_id=? AND state='open'` を D1 で完了させてから新しい permit を発行（= 旧 Worker の batch は assertion で失敗）。放置 `claimed` operation は permit `revoked` 時に同 batch で `operations.state='failed'` に更新（`claimed` かつ同 permit のもののみ）。認可の commit 時再検査: mutation batch に「principal が有効（`users.disabled_at IS NULL`）、credential が有効（`app_passwords.revoked_at IS NULL AND expires_at > now`、share は `shares.version = ?` かつ `disabled_at IS NULL`）」の EXISTS assertion を含める（対象 principal 種別に応じて 1〜2 文）。commit 不明: `batch()` が例外（ネットワーク/timeout）を返し rollback かどうか判別不能な場合、`operations` を最大 3 回（合計 ≤ 5 秒）再読みし、`committed|failed` なら結果を返す、それ以外は **503 + `Operation-Id` ヘッダ + `Retry-After`** を返し、client は `GET /api/v1/operations/:id` で照合（route を manifest に追加）。`claimed` の期限は permit 期限と同じ。
3. **G03 復旧 epoch と backup**: (a) epoch は **ControlDO が唯一の発行者**（単調増加、DO storage に永続）。復旧手順は「ControlDO の `bumpEpoch()` を呼び、その値を D1 `control.epoch` に複製」に修正（D1 側の `+1` を削除）。ControlDO storage 自体を失った場合は `max(D1 control.epoch, 現在時刻の秒) + 1` を初期値にする（単調性の保証）。(b) **journal は廃止**し、D1 の **Time Travel（point-in-time restore、30 日）を第一の復旧手段**、`wrangler d1 export` の logical export（FTS 除く）を第二（アカウント喪失・別リージョン）とする。backup は「commit watermark = export 直前に `control.backup_barrier_op` に記録した最新 committed op_id」の時点状態として復元し、**反映済み operation の terminal state は保存**（`failed` 化しない）。watermark 以降の operation は restore 後に存在しないので、client の照合は 404 → client は「未確定・再送可（Idempotency-Key 同一）」として扱う。R2 の orphan blob は GC の orphan scan（`blobs` に無い `u/*/b/*` key を list で検出、35 日 grace）で回収。(c) 保持: Time Travel 30 日 + logical export を「日次、最大年齢 35 日、最少 5 世代」の両条件で定義。(d) 復旧前に GC の in-flight R2 delete を quiesce（ControlDO `gc_paused=true` → gc job の lease 期限経過を待つ）する条件を追加。
4. **G04 trash/GC**: `trash_members(trash_op_id, node_id, PRIMARY KEY(trash_op_id,node_id))` を trash commit 時に確定（既に `deleted_at IS NOT NULL` の子は含めない）。restore/purge の全 chunk は `WHERE node_id IN (SELECT node_id FROM trash_members WHERE trash_op_id=?) AND trash_ops.state=? AND permit assertion` で fence。FK 削除順序表（`node_tags, node_media, node_audio, library_items, user_reading_state, user_playback_state, shares, share_grants, node_versions, locks, uploads(parent), search_index, nodes`）を §11 に追加。全参照追加（`nodes.current_blob_id`、`node_versions`、`gc_pins`）は共通 assertion `NOT EXISTS (SELECT 1 FROM blobs WHERE id=? AND state IN ('deleting','deleted'))` を含める。DDL に CHECK を追加: `quota_bytes >= 0`、`used_bytes >= 0`、`reserved_bytes >= 0`、`physical_bytes >= 0`、`revision >= 1`、`state IN (...)`。space owner と root owner の整合はアプリ assertion + 修復 job の検査項目。`blobs.state` と `gc_candidates.state` は同 batch で更新。restore 開始条件に GC quiesce を追加。
5. **G05 upload**: single 経路を追加: `POST /api/v1/uploads`（`mode: 'single'|'multipart'`、size 申告）→ single は `PUT /api/v1/uploads/:id/content`（body を **そのリクエスト内で** staging key `u/<owner>/b/<blobId>` へ `R2.put(key, request.body, {sha256?})` ストリーム保存、既知長必須）→ `POST /api/v1/uploads/:id/complete`（メタデータ commit）。public upload-only も同 3 route の `/api/v1/public/shares/:token/uploads/...` 版。0 byte は single 固定。失敗課金台帳: `blobs.state` に `staging`（R2 実在・未 commit、physical に計上、reservation 保持）を追加し、complete 失敗 → `orphan`（reservation 解放、physical は R2 delete 確認後に減算、GC 対象）。`physical_charge_state` 列は削除し `blobs.state` に統一。late part: 「part attempt の結果不明が残る upload は新 attempt を開始しない → その upload 全体を `aborting` へ遷移し R2 abort、client は新しい upload（新 R2 upload id）で再開」に確定。`completing` と abort の競合: `completing` に入ったら abort 要求は 409、complete の応答不明は R2 `head()` 照合で収束。orphan multipart（upload ID 永続化前の停止）は **R2 bucket lifecycle rule「incomplete multipart uploads を 7 日で abort」**で回収（Workers API に list multipart が無いため）。
6. **G06 bootstrap・資格情報**: bootstrap は「`OWNER_EMAILS`（または `OWNER_IDENTITIES` = iss+sub）に一致する identity の初回ログインのみ」+ `control.bootstrap_done_at IS NULL` 条件付き UPDATE。signup は既定 `false`（`settings.signup_enabled`）、bootstrap 前は全 login 拒否（owner 以外）。最後の `app_admin` の停止・削除・降格を禁止（assertion）。admin 移譲は「新 admin 昇格 → 旧 admin 降格」の 2 操作。§14 に用途別 key inventory 表（`SIGNING_KEYS`(kid ring), `CSRF_KEY`, `CONTENT_SESSION_KEY`, `APP_PASSWORD_PEPPER`）+ 通常/緊急 rotation 手順。password record（share password、app password）に `kdf`, `kdf_params`(iterations), `kid` を保存。失効表: 事象（user disable / app logout / app password revoke / share disable / share owner disable / epoch bump）× 対象（Access session / private API / app password / share / content-session Cookie / ticket / job）× 最大遅延。user 停止時は所有 public share を全て `disabled`。app logout は `POST /api/v1/auth/logout` が content-session を D1 で失効（`content_sessions.revoked_at`）してから Access logout へリダイレクト。
7. **G07 route/CSRF**: manifest に route ごとの **CSRF profile** 列を追加: `same-origin-json`（既定、`Sec-Fetch-Site: same-origin`）/ `cross-origin-content`（content origin の `POST /session` と `OPTIONS /session`: `Origin` == app origin allowlist、`Access-Control-Allow-Origin` を固定値で返し `Allow-Credentials: true`、preflight 応答）/ `dav`（Basic 認証のみ）/ `public-form`。**service automation upload は v1 非提供**（`/api/v1/automation/*` は read-only の list/metadata のみ）。不足 route を追加: `GET /api/v1/zips/:id`（ZIP 配信、ticket 必須）、public ZIP、`PUT /api/v1/nodes/:id/star`、`GET /api/v1/shared-with-me`（DAV `/dav/Shared/<mount>` の対応表）、tags CRUD、admin: user disable / admin transfer / lock force-unlock、`POST /api/v1/csrf`、`GET /api/v1/operations/:id`、public edit の MOVE は **非提供**と明示。operation enum を単一表に統一（`node.restore` に統一、`state.write` を `reading_state.write`/`playback_state.write` に分割）し、operation → 必要 scope → operand 種別の完全表を §4 に。
8. **G08 client thumbnail**: **v1 では client thumbnail 受付を無効化**（route 削除、§18 に「有効化する場合の条件: node 単位 key、再 encode、世代 CAS」）。
9. **G09 費用・非開示・ticket**: §13 に以下を復活・一元化: upload part ごと 3 attempts / 累積 part calls ≤ parts×3 / 累積 bytes ≤ declared×3; COW refs 上限 (1,000/blob); dead property 上限 (node 100 / user 100,000, 各 8 KB); bulk 受付 1,000 node; upload-only の自動 rename と同形 201 receipt（確定名非開示）、share 単位 reservation; ticket は用途別 claim (`content|thumb|page|zip|track`)、個別 cancel、share expiry で clamp、content-session 更新時に既存 budget ID を継承（budget は `content_sessions.budget_id` で管理し、新 session 発行でも同 user+share の budget ID を再利用、上限 = 対象合計 bytes×3 かつ 1,024 requests / 10 分）; 全 content/page/entry/public route を同 budget に接続; ZIP は STORE のみ、exact size は同じ serializer の dry-run で算出; TicketDO → **廃止し content_sessions を D1 + budget カウンタは per-session の DO (`BudgetDO`, id = budget_id)** に変更（lease TTL 10 分、alarm で精算、storage 上限 1 MB）; maintenance job の 1 invocation 予算（node 1,000 / blob 1,000 / R2 API 2,000 / 25 秒）; 保護共有の OG は汎用固定文言; 認可済み応答は `Cache-Control: private, no-store`。
10. **G10 search/Gallery**: `search_index(node_id, text_norm, tokens)` を分離: `text_norm` = NFKC + casefold + カタカナ→ひらがな統一の原文、`tokens` = bigram 空白区切り（FTS5 external content, `tokenize='unicode61'`）。同期は fsMutation の同 batch で `INSERT/UPDATE/DELETE` を発行（FTS5 external-content の `INSERT INTO fts(fts, rowid, ...) VALUES('delete', ...)` 手順を明記）。MATCH は各 bigram を `"..."` でクォートし `"` をエスケープ。最終 substring 照合は `text_norm LIKE` で行う。scope 走査は CTE に `LIMIT 10,000` を入れ「不完全結果 (`truncated: true`)」を返す。Gallery CTE は候補 `LIMIT 50,000` を強制し `current_blob_id = node_media.blob_id AND generator_version = ?` を条件に含める。PROPFIND fixture に 1,000 child × 20 property を追加。index は実 SELECT 列を含む covering index に修正（または「covering」表記を削除）。
11. **G11 DAV profile**: §7 に「DAV protocol profile」表を追加: `If` ヘッダの文法（tagged/untagged list、`Not`、複数 list、上限 list ≤ 16 / token ≤ 16）と評価規則（いずれかの list が真なら通過、lock token submission は評価とは別に「提示された token 集合」として収集）、collection revision を増やすイベント一覧（child create/delete/rename/move-in/move-out/PROPPATCH）、`/dav/Shared/<mount>` の予約名（`Shared`、`.ncf-*`）と mount 名規則（`<share_id_short>-<name>`、不変）、PROPPATCH 失敗時の応答（全 rollback、成功したはずの property も `424 Failed Dependency`）、dead property 保存モデル（namespace URI + local name をキー、値は正規化 XML 断片文字列、mixed content 可、8 KB）、XML 受入範囲（標準 5 entity + numeric character reference `&#...;`/`&#x...;` を許可、DTD/外部 entity/内部 entity 宣言は拒否）、lock-null 相当は「未存在 URL の LOCK = parent への `node.create` operand + 空ファイル作成（RFC 4918 §7.3 の locked empty resource）」、protected live property 一覧（`getetag, getcontentlength, getlastmodified, resourcetype, lockdiscovery, supportedlock, creationdate`）、`Content-Length` 欠落 → 411、`If-Match` 必須箇所欠落 → 428。
