# 暗号化の敵対的レビューへの対応

対象レビュー: `fc1ba1b`。レビューの指摘を受け、署名・鍵登録・暗号化必須ポリシーを修正中。以下は受け入れ条件であり、完了・配備済みの記録ではない。実行結果は末尾と `IMPLEMENTATION_STATUS.md` に記録する。

## 受け入れ条件

| 指摘 | 修正と確認すること |
| --- | --- |
| 公開鍵だけで所有者のファイルを偽造できる | 所有者の登録済み署名鍵で、全受信者ラップと暗号化メタデータを含むヘッダーを検証する。コンテナーが自己申告した公開鍵だけで信頼しない。別の署名鍵、署名なし、署名後の変更を拒否する。 |
| 一般利用者の鍵を管理者鍵として固定できる | Access の現在の本人に鍵を登録し、RSA の復号と署名鍵の所持を確認する。管理者一覧は現在の有効な `app_admin` から取得する。公開鍵ファイルと一覧の照合に失敗したら固定・新規アップロードを拒否する。 |
| 管理者のラップ破損を所有者が検出できない | ラップの変更はヘッダー署名で検出する。正規の所有者が故意に壊れたラップに署名する場合は署名だけでは検出できないため、管理者による実復号の確認を別の状態として記録する。未確認を「復旧可能」と表示しない。 |
| `.ncf` という名前を暗号化の証明にしている | 実際の R2 ヘッダーを検証してから、blob と所有者に結び付いた記録を確定する。画面はこの記録を参照する。名前だけが一致する平文を暗号化済みと扱わない。 |
| 変更・共有の禁止が UI のみ | API、WebDAV、フォルダー経由も含めて、対象 blob の記録を確認する。画面を使わない要求でも禁止が成立することを検証する。 |
| 暗号化必須フラグがブラウザーのみ | 新しいファイルの書き込み・確定でサーバーが署名付き暗号化契約を確認する。契約に対応しない API、WebDAV、公開アップロードによる平文の書き込みを拒否する。開始後にポリシーが変更されたアップロードも確認する。 |
| JavaScript 配信元への信頼が必要 | 設定画面と利用者向け文書に、配信コードを改ざんできるサービス提供者には対抗できないことを示す。鍵登録や署名を、この境界への対策と説明しない。 |

## 互換性と鍵の扱い

- 復旧 JSON と既存 RSA 鍵は維持する。独立した署名鍵を既存の復旧秘密から用途を分けて導出し、RSA 鍵を署名に流用しない。
- 復旧 JSON はそれだけで秘密鍵を復元できる。公開鍵登録に送るのは公開情報と一時的な所持証明だけで、復旧 JSON・秘密鍵・復旧秘密は送らない。
- 旧形式の暗号化には送信者の署名がない。復号できるだけでは過去の送信者を証明できない。本人が内容を確認したうえで、現在の node/blob とヘッダーを結び付けた署名を追加する。
- 実運用中の管理者の3件は、以前の全バイト検証で保存した SHA-256 と照合してから引き継ぐ。一般利用者2人の鍵設定は、ユーザーの指示どおり今回の運用対象に含めない。
- 管理者公開鍵の交換は、既存ファイルのラップを自動更新しない。鍵の無効化は、すでに取得された暗号文や秘密鍵を消去できない。既存の鍵登録を同じ API で上書きしない。

## 保証の範囲

ヘッダー署名は登録済みアカウントによるヘッダーの承認を示す。暗号化された各チャンクは AES-GCM で認証する。復号鍵を持つ正規の受信者に対し、ファイル全体の第三者証明を提供する方式ではない。巻き戻し、提供停止、削除、配信 JavaScript の差し替えまで防ぐとは説明しない。

管理者の復号確認は、その時点の鍵と対象 blob に対する確認である。将来の秘密鍵の紛失や、外部バックアップの欠損を防ぐ保証ではない。暗号化バックアップの復元試験は別途必要。
