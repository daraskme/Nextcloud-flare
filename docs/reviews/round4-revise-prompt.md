### 確定方針（ラウンド4）

1. **fsMutation の完全 SQL 契約 (§7.1 A〜F)**: §5 に以下を実 SQL で記載する: (a) `control` 1 行テーブル（`epoch`, `bootstrap_done_at`）、(b) claim: `INSERT INTO operations(op_id, principal_id, credential_id, kind, state, ...) ... ON CONFLICT DO NOTHING` → 影響行 0 なら既存 op の終端結果を返す、(c) 各 step UPDATE/INSERT は `WHERE ... AND revision = ? AND deleted_at IS NULL AND (SELECT epoch FROM control) = ?` を持つ「proof 条件付き文」とし、(d) 最終 barrier: `UPDATE operations SET state='committed' WHERE op_id=? AND state='claimed' AND (SELECT epoch FROM control)=?` を batch 末尾に置き、`D1Result.meta.changes` を **全 statement で検証**、いずれかが期待値と異なれば batch は成功していても **論理的に失敗扱い**にし、補償として `operations.state='failed'` を別 batch で書く（batch は D1 で暗黙トランザクション、1 文でも失敗すれば全 rollback — 公式仕様を引用）。(e) 例外 catch を「batch 拒否（rollback 済み）」と「batch 応答喪失（commit 不明）」に分け、後者は `operations` を op_id で再読みして状態を確定するまで client に 5xx を返さない（`claimOperation` の再送で解決）。(f) LockDO permit は `permit_id` + `expires_at` を持つ **fence token** として D1 の `operations.permit_id` に記録し、batch 内の proof 条件に `permit_id` の一致は含めない代わり、LockDO は permit 期限切れ後に「D1 の `operations` を読んで committed か確認してから」lock を解放する（quiesce 完了条件 = 当該 space の open permit が 0 かつ期限切れ permit の D1 照合完了）。(g) MOVE の lock 終了は「commit 後、LockDO へ `release(permit_id, result)` を送る」で確定し、送信失敗は permit 期限で回収。
2. **UploadDO 状態機械 (§7.3)**: `created → uploading → completing → completed | failed | expired | aborted` の各遷移に「前提・副作用（R2 API 呼び出し）・冪等鍵・失敗時の再試行/回収」を表で固定。`completing` は R2 `completeMultipartUpload` の応答喪失に備え `complete_attempts` と `r2_etag` を保存し、再試行は R2 `head()` で実在照合してから `completed` へ。part retry は同一 partNumber の再送で上書きされる R2 仕様を前提に「最後に成功した etag のみ保持」。zero-byte / 5 MiB 未満は single PUT 経路（multipart 不可）を明記。課金（physical_bytes）は `completed` 確定と同 batch。
3. **trash_ops 状態統一 (§7.3 / §9)**: `trash_ops.state` を `pending → trashed → (restoring → restored) | (purging → purged)` に統一し、v0.4 に残る `removed` 等の異表記を全置換。「公開時点（共有・ticket が失効する瞬間）= `trashed` commit」「GC pin = `gc_candidates.pinned_by`」「不可逆点 = `purging` に入った時点で restore 不可」を SQL 条件で明記。
4. **CONTENT_HOST ticket 搬送 (§7.5)**: 採用方式を **「短命 content-session Cookie」** に確定: SPA は `POST /api/v1/content-session` (Access 認証) で `{node_id|share_id, blob_id, scope}` 群に対する ticket を取得 → CONTENT_HOST の `POST https://<content>/session` に **fetch (credentials: include, CORS allowlist = app origin のみ)** で送信 → CONTENT_HOST が `__Host-ncf_cs`（`Secure; HttpOnly; SameSite=None; Path=/; Max-Age ≤ 600`）を設定。以後 `<img>/<video>/<audio>/<iframe>` の `src=https://<content>/c/<node_id>/<blob_id>[/...]` は Cookie で認可（URL に secret 無し）。Range 対応。単一 host 構成では同じ Cookie を `__Host-ncf_cs` として同一 host で使い、CSP/attachment 制限を維持。blob URL 方式は「≤ 32 MiB の text/markdown/pdf.js 入力のみ」に限定。
5. **EPUB reader の実行モデル (§7.5)**: 「reader shell（信頼済み、アプリの静的アセット、CONTENT_HOST 上の `/reader/` に配置）」と「出版物コンテンツ（sandbox iframe）」を分離する二重 iframe 構成: app origin → `<iframe src=https://<content>/reader/index.html sandbox="allow-scripts allow-same-origin">`（shell、CSP: `script-src 'self'`）→ shell 内 `<iframe sandbox>`（allow-scripts 無し、`srcdoc` に **サーバで sanitize 済み** XHTML を注入、CSP: `default-src 'none'; img-src 'self' data: blob:; style-src 'self' 'unsafe-inline'; font-src 'self' data:`）。CFI・pagination は shell が sanitize 済み DOM を自身で解析して実装（内側 frame の DOM 操作は shell が `srcdoc` を再生成する形で行う）。出版物由来の `<script>`, `on*`, `javascript:`, 外部 URL は sanitize で除去（サーバ側 Queue job で sanitize 済み XHTML を派生物として R2 に保存、Range 配信）。v1 は「リフロー、目次、CFI 位置、フォントサイズ/テーマ」のみ、固定レイアウト EPUB/メディアオーバーレイ/JS 依存 EPUB は非目標。
6. **共有 landing の公開アセット (§7.5)**: `/s/*` 用の JS/CSS を **別バンドル `public-share.[hash].js`** として `/public-assets/*` から配信（Access Bypass 対象、manifest に `auth: public` で登録、private SPA バンドルとは共有しない、Subresource Integrity 付き）。
7. **WebDAV Class 2 (§7.4)**: **選択肢 1 を採用**: 通常 locked mutation（PUT/DELETE/MOVE/COPY/PROPPATCH/MKCOL 配下）にも RFC 4918 §6.4 に従い **lock token 提示 + 認証 principal が lock creator と一致** を要求（app password は user principal の代理なので、同 user の別 app password は一致とみなす。service token は別 principal）。ラウンド3 の「creator 照合しない」記述を撤回し、round3-resolution の該当行も「R4 で再変更」と注記。UNLOCK も同じ規則。同期 WebDAV COPY/MOVE は「同 owner 内の ≤ 1,000 node かつ ≤ 10 GiB のみ同期実行、超過は 507 Insufficient Storage ではなく **403 + `<D:error><ncf:too-large-for-dav/>`**」とし、REST job へは自動フォールバックしない。XML fixture（PROPFIND 空/allprop/propname/prop、200+404 propstat、PROPPATCH 424、LOCK 200/201、refresh、UNLOCK 204、423 lock-token-submitted、propfind-finite-depth、COPY/MOVE Overwrite/Depth/207）を §7 に規範例として追加（各 ≤ 30 行）。XML パーサは fast-xml-parser を **adapter (`davXml.ts`) で包み**: `preserveOrder:true, ignoreAttributes:false, parseTagValue:false, trimValues:false, processEntities:false` + 事前に DTD (`<!DOCTYPE`) を拒否 + 標準 5 entity のみ手動 decode + namespace URI + localName で解釈 + depth/要素/属性/サイズ予算。
8. **KDF / WASM / fflate (§8)**: (a) 共有パスワード KDF は **PBKDF2-HMAC-SHA256 100,000 回**を v1 既定（workerd 既定 limit 以下）、staging gate として「600,000 回の受理有無を実測 → 受理されれば設定値で引き上げ」を §18 に。scrypt は不採用（メモリ上限の保証が無い）。(b) SHA-256 streaming は `crypto.DigestStream('SHA-256')` を採用、hash-wasm は不採用。multipart の全内容 SHA-256 は「client が計算して complete 時に申告、サーバは各 part の `DigestStream` 結果を保存し、順序付き全内容 hash はサーバでは計算しない（`sha256_verified` は single PUT のみ true、multipart は `client_sha256` として別列に保持）」。(c) ZIP 生成は fflate の **同期 streaming API (`Zip`, `ZipPassThrough`, `ZipDeflate`)** のみ使用（`Async*` 禁止）。ZIP 展開は自前の central directory パーサ + `DecompressionStream('deflate-raw')`（fflate 不使用）。(d) `@hono/zod-openapi` を採用、版は package.json で固定。(e) 依存ライブラリ表を §13 または §14 に追加（名前 / 用途 / Workers 上の制約 / 禁止 API）。
9. **backup / restore with FTS (§4.5, §9)**: D1 logical export は FTS5 仮想テーブルを含めないため、backup 対象は **通常テーブルのみ** とし、restore 手順に「`search_index` FTS を `INSERT INTO ... SELECT` で再構築 → `control.epoch += 1` → LockDO/UploadDO を stale 化」を明記。journal (`operations`, `outbox`) を含めて整合点は「backup 開始時に `control.backup_barrier` を書き、それ以降の op_id を restore 後に `failed` 扱い」。月 1 回の restore drill を §14 運用に。
10. **制限値の修正 (§1)**: レビューの §1.1〜1.3 の「誤り」「欠落」を全て修正（Queues のメッセージサイズ・batch 単位、Images の入力 bytes 上限、D1 の bind 数 100 / SQL 長 / rows read、DO の値サイズ、R2 の part 数・サイズ範囲、KV 値サイズ、Cron 頻度、Worker CPU/メモリ、subrequest 数等）。数値は必ず一次資料の URL を脚注で付け、確信のないものは「要確認」。**error mapping 表**（Cloudflare 例外 → HTTP status → client 再試行可否）を §13 に追加。
11. **D1 予算 (§4.3, 4.4, P1)**: 一覧 / search / PROPFIND Depth:1 / gallery / ancestor CTE の **実 SQL とインデックス**を §3/§12 に記載し、各 fixture（子 1,000 / 10,000、深さ 64）で「query 数 ≤ N、bind ≤ 100、rows read ≤ M、duration ≤ T ms」の予算表を §15 に置く。`IN (...)` は 100 bind 超で分割。一覧上限 200 件 / page を D1 rows read 予算と結び付けて説明。
12. **DO 容量・alarm・stale (§5, P1)**: LockDO / UploadDO / ControlDO それぞれに「同時 in-flight 上限、alarm retry 上限と枯渇時の挙動、eviction 後の再初期化（D1 から再構築 vs stale 拒否）、並列枠リーク試験」を §14 に表で。
13. **CI 三段階 (§6)**: unit (vitest, pure TS) → integration (`@cloudflare/vitest-pool-workers`, Miniflare: D1/R2/DO/Queues local) → staging smoke (実 Cloudflare、`wrangler deploy --env staging`、Access Bypass・CONTENT_HOST・PBKDF2 受理・Images・Queue 実配信を検査)。Miniflare で再現できない項目一覧を §15 に。
