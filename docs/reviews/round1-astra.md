## B-01. 同一 R2 キーへの上書きと D1 更新の間で、内容・メタデータが不整合になる

**対象：§3「R2 キー設計」「整合性ルール」、§5、§6、§7、§13**

### 何が問題か

現在の本体キーは `u/<ownerId>/o/<nodeId>` で、上書きも同じキーに対して行う設計です。

次のような状態が発生します。

1. 既存ファイルの R2 本体を上書きする。
2. R2 書き込みが成功する。
3. D1 の `size / etag / mime / used_bytes` 更新が失敗する。
4. 利用者には旧メタデータと新しい内容の組み合わせが見える。
5. 旧内容は既に失われている。

マルチパートの `complete()` も、成功すると新しい内容がそのキーで可視化されます。**「complete まで見えない」ことは、D1 更新との原子性を保証しません。**

さらに、二つのアップロードが同じノードを上書きすると、R2 と D1 の完了順序が異なる可能性があります。

### なぜか

- R2 と D1 をまたぐ分散トランザクションはありません。
- `UploadDO(uploadId)` はアップロード単位の調停であり、**同一ファイルへの複数アップロード間の競合**を防ぎません。
- R2 Workers API の `put()` には条件付き書き込みがありますが、公開されている `R2MultipartUpload.complete()` のシグネチャには同じ `onlyIf` オプションがありません。
- D1 の Time Travel は、上書き済みの R2 内容を元に戻しません。

### 具体的な修正案

**論理ノード ID と、不変の内容オブジェクト ID を分離してください。**

例：

```text
nodes.id                 = 論理ファイルの恒久 ID
nodes.current_blob_id    = 現在の内容
blobs.id                 = 内容世代の ID
blobs.r2_key             = u/<ownerId>/b/<blobId>
nodes.revision           = メタデータ更新用の世代番号
```

書き込み手順を以下に固定します。

1. D1 に操作 ID、期待する旧 revision、アップロード先、新 blob ID、クォータ予約を記録。
2. **新しい不変キー**に R2 書き込み。
3. 実サイズ・必要な整合性検査を確定。
4. D1 の原子的な処理で、期待 revision を条件に参照先を切り替える。
5. 同じ確定処理でクォータ・監査・後処理 outbox を更新。
6. 旧 blob は直ちに消さず、保持ポリシーに従って GC。

失敗時は旧ファイルがそのまま残ります。新 blob が孤立することはありますが、これは後処理で回収できます。

**UI の「ファイルバージョン履歴」を後段にすることと、内部の安全な世代管理を後段にすることは別です。**

## B-02. 「R2 が真、D1 は再構築可能」が現在のメタデータでは成立しない。GC と組み合わさるとデータ消失を拡大する

**対象：§3、§13、§17-1**

### 何が問題か

R2 の `customMetadata` にあるのは `nodeId / ownerId / sha256` だけです。これでは少なくとも以下を復元できません。

- ファイル名。
- ファイルの親フォルダ。
- 削除状態、削除日時、復元先。
- 共有、アプリパスワード、ユーザー設定。
- WebDAV dead properties。
- 現在どの内容世代を採用していたか。
- 監査履歴。

§13 のフォルダ marker を追加しても、**フォルダ自身の情報だけでは各ファイルの名前と所属は復元できません**。marker に子一覧まで持たせるなら、今度は rename/move ごとの二重更新と、その整合性管理が必要です。

また、D1 を過去へ戻した後に現在の R2 と比較すると、正しいオブジェクトが「索引にない孤立物」と判定されます。24時間という猶予だけでは安全性を保証できません。

### なぜか

この設計では、R2 は内容の正本ですが、**D1 は名前空間・権限・状態の正本**です。D1 を単なる索引と扱うと復旧要件を満たせません。

### 具体的な修正案

推奨は、正本を明確に分けることです。

> R2：不変のファイル内容  
> D1：論理名前空間、参照、権限、状態の正本

そのうえで：

- D1 の定期エクスポートと、対応する blob 集合・世代の復旧方針を定義。
- Time Travel 後の照合手順を定義。
- 復旧モード中は GC を停止。
- 未完了操作、旧世代、サムネイル、バックアップ、marker を GC 対象から適切に区別。
- GC は「見つからないので即削除」ではなく、候補記録 → 猶予 → 再検証 → 削除。
- D1 読み取り失敗を「参照なし」と解釈しない。
- 復旧演習をリリース条件にする。

R2 だけから完全再構築できることを要件にするなら、**全メタデータのスナップショット／操作ログと、その確定プロトコル**が別途必要です。

## B-03. ルート直下の名前一意性が SQL で保証されない。ツリーの不変条件も不足している

**対象：§3、§4.3、§5、§7**

### 何が問題か

次の UNIQUE INDEX は `parent_id IS NULL` のルート直下では期待どおりに機能しません。

```sql
UNIQUE (owner_id, parent_id, name)
WHERE deleted_at IS NULL
```

SQLite の UNIQUE 制約では NULL を含む値について重複を許すため、同じユーザーのルート直下に同名の有効ノードを複数作れます。

また、以下の禁止条件が明記されていません。

- ファイルを親にする。
- 別 owner のノードを親にする。
- フォルダを自分自身または子孫へ移動する。
- 移動によって子孫の深さが64を超える。
- 削除中・回収箱内のフォルダへ新規作成する。

### なぜか

パス解決が一意でなくなり、WebDAV PUT がどのファイルを更新するか不定になります。循環ができると祖先認可・削除・検索の再帰処理も破綻します。

### 具体的な修正案

以下のいずれかを採用します。

- **ユーザーごとに実体のある root ノードを作る**。通常ノードの `parent_id` は非 NULL。
- ルート用に `UNIQUE(owner_id, name) WHERE parent_id IS NULL AND deleted_at IS NULL` を別途追加。

加えて：

- 親の存在・種類・owner・有効状態を検証。
- 自己／子孫への MOVE を拒否。
- 子孫も含めた最大深さを検証。
- 競合する MOVE 間でも条件が崩れない原子的処理を設計。
- owner をまたぐ移動は v1 では禁止、または明示的な copy＋delete とする。
- 内部共有先への作成では、**actor と owner を区別し、owner は保存先スペースに合わせる**。

## B-04. クォータの先行チェックだけでは並列アップロード・申告サイズ偽装を防げない

**対象：§3、§6、§8、§11、§13**

### 何が問題か

`used_bytes + size <= quota` の先行チェックは、予約ではありません。

例えば残容量10 GBに対して8 GBのアップロードを二つ開始すると、双方が開始チェックを通過します。また、申告サイズより大きい内容を送った場合の強制的な制限も未定義です。

公開の upload-only 共有が加わると、所有者の費用を第三者が消費できます。

### なぜか

`used_bytes` の加算自体が原子的でも、**チェックから完了までの容量確保**は原子的になっていません。

### 具体的な修正案

- `reserved_bytes` と、操作 ID に紐づく予約レコードを導入。
- 開始時に以下を原子的に保証。

```text
used_bytes + reserved_bytes + new_reservation <= quota_bytes
```

- 各パートの実バイト数を検証し、最終合計を宣言サイズと照合。
- サイズ不明の PUT は予約容量を段階的に増やすか、上限分を予約。
- 完了・abort・期限切れで予約の確定／解放を**一度だけ**行う。
- コピー、上書き差分、回収箱、旧世代、派生物の課金対象を定義。
- upload-only 共有にファイルサイズ・件数・同時セッション・共有全体容量の上限を設ける。
- 内部共有へのアップロードは actor ではなく保存先 owner のクォータに計上。

D1 `batch()` 内の条件付き UPDATE が0行だっただけでは、後続文が自動的に失敗するとは限りません。**条件不成立時に全体が確実に確定しない SQL 設計**が必要です。

## B-05. 回収箱の再帰フラグ更新では、以前に削除した子の復活やパージ失敗が起きる

**対象：§3、§5、§11**

### 何が問題か

例：

1. `A/B.txt` を削除。
2. 後からフォルダ `A` を削除。
3. `A` を復元し、子孫の `deleted_at` をすべて NULL にする。
4. 以前に独立して削除した `B.txt` まで復活する。

逆に、親削除で既に削除済みの子の `deleted_at` を更新すると、その子の保持期限が勝手に延長されます。

さらに `shares.node_id REFERENCES nodes(id)` に `ON DELETE` 方針がなく、共有レコードが残ったノードの削除は外部キー違反になります。記載の順序では **R2 本体だけ削除した後で D1 delete が失敗**します。

### なぜか

- `deleted_at` と `trash_root` だけでは、複数回の削除操作の所属を表せません。
- D1 は外部キー制約を既定で強制します。
- 100行ずつの更新途中にリクエストが来た場合の可視性も未定義です。

### 具体的な修正案

- `trash_entries`／`delete_operation_id` を導入し、どの削除操作で非表示になったかを管理。
- 既に削除済みのノードは、後続の削除操作に無条件で取り込まない。
- 復元は、その削除操作に所属するノードだけを対象にする。
- 親が存在していても、回収箱内・削除中・別 owner なら復元先にしない。
- 大きなツリーは最初にルートを論理的に不可視にし、子孫処理は再開可能なジョブにする。
- パージ対象を manifest／tombstone として固定。
- 共有、props、子ノード、サムネイル、旧 blob の削除・保持方針を決める。
- クォータ減算とジョブ確定は冪等にする。

## B-06. WebDAV ロックの分散単位と適用範囲が不十分

**対象：§1、§3、§4.2、§7、§8、§13**

### 何が問題か

`LockDO(userId)` の `userId` がアクセス主体を意味するなら、同じ共有ファイルを owner と grantee がそれぞれ別 DO でロックできてしまいます。

また、WebDAV で LOCK されていても、REST API やアップロード complete がロックを確認しなければ更新を通せます。

`ro` スコープに書き込み用 LOCK を許可すると、読み取り専用の資格情報で他者の書き込みを妨害でき、未存在 URL への LOCK では空リソース作成の扱いとも衝突します。

### なぜか

- ロック対象は「操作ユーザー」ではなく、共有を含めた**同一の実体名前空間**です。
- 「ロック確認 → Worker で更新」の間にも競合が入れます。
- DO が単一スレッドであることは、外部 I/O をまたぐ処理全体が自動的に排他されることを意味しません。

### 具体的な修正案

- DO の単位を `spaceId`／保存先 owner など、**共有される実体側**に統一。
- 全書き込み経路を共通の fs mutation サービスへ集約。
- ロック確認と書き込み確定の間を、操作予約・世代条件・適切な調停で保護。
- ロックを永続化し、期限は各リクエストでも検査。
- 読み取り専用 principal の write LOCK は原則拒否。
- `Depth: infinity` の祖先ロック、作成先の親ロック、COPY/MOVE の destination 側ロックを扱う。
- ロック token の所有 principal／資格情報と、失効時の扱いを定義。

**注意：node ID にロックを付けて MOVE 時も単純追従させる実装も不適切です。**  
RFC 4918 では MOVE で元の write lock を移動先へそのまま移してはいけません。内部の排他制御と、WebDAV の URI 名前空間に対するロック意味論を分けてください。

## B-07. UploadDO の永続化・完了・中断・再試行の状態機械が足りない

**対象：§3 `uploads`、§6、§13**

### 何が問題か

SQLite-backed DO の採用は正しいですが、`parts: Map<n, etag>` を「保持する」だけでは、以下の障害境界が決まりません。

- DO 再起動でメモリ上の Map が消えた。
- R2 パート保存後、DO 記録前に切断した。
- 同一 part number の再送が並行した。
- complete と Cron abort が競合した。
- R2 complete 後、D1 更新前に停止した。
- 完了応答だけ失われ、クライアントが complete を再送した。

### なぜか

R2、UploadDO、D1 の三者に状態があり、原子的には更新できません。DO の永続ストレージを使っても、外部サービスとの境界は残ります。

### 具体的な修正案

少なくとも以下を定義してください。

```text
initiating
  → active
  → completing
  → committed

active
  → aborting
  → aborted
```

- DO の SQLite にセッション・パート番号・実サイズ・etag・処理世代を永続化。
- 同一パートの並行処理と再送を制御。
- complete 開始前に状態を固定し、以後の新規パート／abort を調停。
- パート番号の重複・欠落・順序・サイズ・総量を検証。
- complete は操作 ID で冪等化し、完了済みなら同じ node／revision を返す。
- R2 complete 済みか不明な状態は、固有 blob キーを使って照合可能にする。
- D1 の一覧用レコードと DO のどちらが各状態の正本か決める。
- R2 側の未完了 multipart lifecycle を、アプリの24時間期限に対する安全網として設定。

`blockConcurrencyWhile()` でアップロード全体を囲めば解決、ではありません。同 API には30秒のタイムアウトがあるため、長い転送は状態遷移で扱うべきです。

## B-08. 共有・資格情報・内部共有を統合した認可の安全条件が未定義

**対象：§4.1〜4.3、§5、§6、§8、§10**

**分類：安全条件の未定義**

### 何が問題か

「owner」「祖先共有」「token 経由」という説明だけでは、以下が決まりません。

- token が有効なだけで、任意の `nodeId` を `/thumb/:nodeId` へ指定できないか。
- upload-only token で既存ファイル一覧や内容を読めないか。
- 内部共有の read 権限で share 作成や再共有ができないか。
- 長時間アップロード中に共有が失効した場合、complete を許すか。
- share Cookie 発行後にパスワード変更・権限変更した場合、旧 Cookie が有効なままか。
- Access JWT と `ro` アプリパスワードが同時に付いた場合、どちらの権限を使うか。

特に「Bypass ルートでも Access JWT が付いていれば通常ユーザーとして扱う」は、実装によっては資格情報のスコープを意図せず拡大します。

### なぜか

共有 token は単なるログイン状態ではなく、**対象・操作・期限が限定された capability**です。別の認証情報が添付されていることと、能力を自動合成することは別です。

### 具体的な修正案

- principal を `user / app_password / link_share / service_token` に型分け。
- 操作ごとの許可表を作る。
- 認証方式の選択・併用ルールを固定し、権限を暗黙に足し合わせない。
- 共有 root 自身と、その有効な子孫だけを対象にする。
- content、thumb、preview、ZIP、children、upload complete の全経路で同じ判定を実施。
- upload-only は「新規受け取り」に限定し、一覧・読み取り・既存名上書きを原則禁止。
- Cookie に share ID、失効世代、期限を含め、現在の共有状態と照合。
- 権限・取り消しの判定を KV の古い値だけで済ませない。
- アップロード完了時にも保存先・権限・削除状態を再検証。

## B-09. 公開 API のパスと Access Bypass の設定が一致していない

**対象：§4.1、§5、§14**

### 何が問題か

REST API のベースは `/api/v1` ですが、公開共有 API は表上で `/public/shares/:token` です。通常の解釈では実 URL は：

```text
/api/v1/public/shares/:token
```

一方、Bypass 設定は：

```text
/api/public/*
```

です。

### なぜか

記載どおりの設定では、公開共有ページからの API アクセスが Access ログインに遮られます。修正時に `/api/*` を広く Bypass する、といった誤対処も誘発します。

### 具体的な修正案

- 公開 API の絶対パスを決定。
- Hono、Access、Static Assets、CSRF、CORS のルート表を共通化。
- `/dav` と `/dav/`、`/s` と `/s/`、`/.well-known/*` の境界を明示。
- `/.well-known/*` 全体を無条件で公開するより、必要なパスだけ公開。
- 公開 prefix の未知ルートは、private API や SPA にフォールバックせず拒否。
- IaC 適用後に未認証の実 HTTP リクエストで確認。

## B-10. 全 mutation 共通の CSRF 要件と、共有ページ共通の CSP sandbox が機能を壊す

**対象：§7、§8、§13**

### 何が問題か

「mutation は `Origin` 検証＋`X-Requested-With` 必須」を WebDAV にも適用すると、多くのネイティブクライアントの PUT／MOVE／DELETE が拒否されます。

また、ゼロ JS の共有ページで通常の HTML form を送信する場合、独自ヘッダは付けられません。

共有ランディング全体に bare な `Content-Security-Policy: sandbox` を付けると、パスワードフォーム、スクリプト、ダウンロード等に必要な能力も制限されます。

### なぜか

- Cookie 認証のブラウザ API と、明示的な資格情報を送る WebDAV クライアントは同じ CSRF 方針にできません。
- アプリケーションのランディングページと、未信頼コンテンツのプレビュー文書は別のセキュリティ境界です。

### 具体的な修正案

- Cookie ベース REST mutation：厳格な Origin 検証＋CSRF 対策。
- WebDAV：Cookie にフォールバックしない明示認証、ブラウザ由来の不正 Origin の拒否、CORS 非公開などを別設計。
- SSR form：CSRF token と Origin 検証で対応。
- 共有ランディング：フォーム・必要なスクリプト・画像・ダウンロードに合わせた CSP。
- 未信頼プレビュー：別の sandbox 境界。
- 生コンテンツ：attachment／安全な MIME／nosniff を用途別に設定。

## B-11. アップロードのプラン前提・サイズ算式・長さ不明ストリームの扱いが成立していない

**対象：§0、§5、§6、§13、§15、§17-5**

### 何が問題か

問題は四つあります。

#### 1. Workers Paid と HTTP ボディ上限を混同している

Workers Paid にしただけでは、100 MB 超のアップロードが可能になるわけではありません。制限は Workers の課金プランではなく Cloudflare のゾーン／アカウント側プランに依存します。

#### 2. MB と MiB が混在している

公式の HTTP ボディ制限表は MB 表記です。`100MiB` と同一視して境界値を決めるべきではありません。

#### 3. パートサイズ算式が想定パート数と一致していない

`max(8MiB, ceil(size / 9000))` を1 MiB単位で切り上げると：

| ファイルサイズ | 算式による partSize | パート数 |
|---|---:|---:|
| 100 GB、十進 | 11 MiB | 約8,670 |
| 100 GiB | 12 MiB | 約8,534 |

§15・§17 の約1,100パートとは大きく異なります。

さらに、partSize を90 MiBで打ち切ると任意の5 TiBファイルには対応できません。

- 9,000パート目標なら約791 GiB。
- 10,000パートを使い切っても約879 GiB。

#### 4. 「R2 put は長さ不明ストリームも受ける」は誤り

確認した workerd 実装では、R2 PUT に渡すストリームの長さを取得できない場合、`TypeError` になります。

`request.body` であることだけでは、真に長さ不明のストリームを常に扱える保証にはなりません。

### 具体的な修正案

- `MAX_REQUEST_BYTES`、`MAX_PART_BYTES`、`MAX_FILE_BYTES` を別々に定義。
- 実際のゾーン設定を確認し、境界より余裕のある値を採用。
- 既定 partSize は32〜64 MiBなど、スループット・再送負担・クライアントメモリを考慮して決める。
- パート数を最終計算し、10,000超なら開始前に拒否。
- 長さが分かるストリームはその情報を維持して R2 へ渡す。
- 真に長さ不明の場合は、小さな固定バッファでサーバ側 multipart に分割するか、v1 では明示的に拒否。
- **サーバ側 multipart 化しても、元の1 HTTPリクエストのボディ上限は回避できない**ことを明記。
- エッジが先に返す413では、Worker 独自の案内文を返せない場合があることも UX に織り込む。

根拠：[Workers limits](https://developers.cloudflare.com/workers/platform/limits/)、[workerd の R2 書き込み処理](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/api/r2-rpc.c++)。

## B-12. WASM サムネイルの上限が Worker メモリに収まらず、Images binding の入力上限とも一致しない

**対象：§1、§10、§13、§14**

### 何が問題か

40 MP の RGBA 画像だけで約160 MB必要です。これは Worker の128 MBメモリ上限を超えます。

実際には以下も必要です。

- 圧縮済み入力。
- デコーダの作業メモリ。
- リサイズ元と出力。
- WASM メモリ。
- JavaScript オブジェクト。
- 同じ isolate 上の他の処理。

また、現在の Images binding `.input()` の公式上限は **20 MB** です。設計書の50 MBとは一致しません。

「Images が失敗したら同じ大画像を WASM で処理する」は、最も重い入力を最もメモリ制限の厳しい経路へ流します。

### 具体的な修正案

- Images と WASM で別々の上限を持つ。
- デコード前に、信頼できる方法で幅・高さ・フレーム数を検査。
- WASM は十分小さい画像に限定し、実測でメモリ予算を決める。
- Images の容量超過・未対応形式・不正画像では、無条件に WASM へフォールバックしない。
- batch 10 は配信単位であり、10画像を同時にデコードしない。
- GIF 等は静止画化方針と総フレーム上限を決める。
- HEIC／AVIF／アニメーションの対応は採用プランと codec ごとに確認。

Images binding の存在自体は公式に確認できますが、**対象アカウントでの契約状態、採用形式、Wrangler／ローカルテストの対応は要確認**です。

## B-13. `fflate` の ZIP ストリーミングを、そのまま大容量 ZIP 対応とみなせない

**対象：§5、§8、§13**

### 何が問題か

「最大約900ファイル」は、ZIP のサイズ制約への対策ではありません。100 GBのファイルが1個でも問題になります。

確認した `fflate` のソースでは、ZIP 出力のサイズ・オフセット・data descriptor が通常 ZIP の32bit形式です。ZIP64 の読み取り対応と、大容量 ZIP64 の書き出し対応は別です。

### なぜか

通常 ZIP は、単一エントリサイズやアーカイブ内オフセットなどに4 GiB級の境界があります。ストリーミングはメモリ使用量を減らしますが、フォーマットのビット幅は増やしません。

### 具体的な修正案

次のどちらかを選んでください。

1. ZIP64 を正しく書き出せる実装を選び、Workers 上で検証。
2. v1 は通常 ZIP の安全範囲に総バイト数・単体サイズ・ファイル数を制限し、超過時は開始前に拒否／分割。

採用する `fflate` のバージョンは未固定なので、**その版の ZIP64 書き出し能力は要確認**です。現在確認した実装を前提に、無制限の ZIP 配信は約束できません。

また、出力の backpressure を無視して R2 を読み進めないこと、ZIP 内のパスを正規化して危険な名前を出さないことも必要です。

## B-14. Cron の曜日指定が不正で、KV ロックによる多重実行防止も成立しない

**対象：§11、§13、§14**

### 何が問題か

#### Cron 式

```text
0 3 * * 0
```

Cloudflare Cron の曜日は公式に **1〜7、1が日曜日**です。0を日曜日とする一般的な crontab の前提は使えません。

#### KV ロック

```text
KV lock:<job> with TTL
```

KV は結果整合であり、atomic な「存在しなければ作成」を提供する分散 mutex ではありません。複数実行が同時にロック未存在を見て処理を始められます。

### なぜか

パージ、クォータ減算、multipart abort、GC の並行実行は、二重処理や処理途中の破壊を招きます。

### 具体的な修正案

- 曜日は `0 3 * * SUN` のように表記。
- UTC で動くことを明記。
- DO または D1 の原子的な条件付き lease 取得を使用。
- lease 期限切れ後の旧実行を排除する fencing／操作世代を持つ。
- mutex の有無にかかわらず、各ジョブを冪等化。
- Cron は大量処理を一度で完遂する主体ではなく、再開可能なジョブを起動する主体にする。

## B-15. 「最初にアクセスしたユーザーが owner」は安全な初期化ではない

**対象：§4.1、§4.3、§14**

**分類：安全条件の未定義**

### 何が問題か

Access が許可ドメイン全体を受け入れる構成なら、そのドメイン内の誰が最初にアクセスするかで owner が決まります。並行初回アクセス時の決定方法も未定義です。

### なぜか

認証できることと、最初の管理者になる権限は別です。

### 具体的な修正案

- デプロイ時に owner の許可 identity を明示。
- CLI による bootstrap、または明示 allowlist と一度限りの原子的初期化を使用。
- bootstrap 前は通常登録を閉じる。
- owner 移譲・最後の owner の削除禁止・復旧手順を定義。
- `allow_signup` の既定値を明確化。
- Access 設定や必須環境変数が欠けたら fail closed。

# 2. 設計上の弱点 — Major

## M-01. D1 の「100行単位バッチ」は、制約対応として不十分

**対象：§3、§5、§12、§13**

100行をまとめても、1行10列なら INSERT の bind parameter は1,000個になり得ます。D1 は1クエリ100 parameterです。

また、`db.batch()` を複数回に分けると、全バッチをまたぐ原子性はありません。

**修正案：**

- バッチサイズは行数だけでなく parameter 数・SQL長・実行時間で決める。
- 大規模操作は操作状態を持つ再開可能ジョブにする。
- 一覧の sort ごとに索引と keyset cursor を設計。
- `shares(grantee_user_id, node_id)`、`uploads(state, expires_at)`、`activity(node_id, ts)` 等、実クエリに必要な索引を追加。
- 読み取りレプリカを使う場合は D1 Sessions／primary 読み取りの方針を定義。認可取り消し直後や書き込み直後の読み取りを古い結果で判定しない。

---

## M-02. WebDAV パス解決の KV キャッシュは stale な読み取り以上の問題を起こす

**対象：§1、§4.3、§7**

例えば `/A.txt → node1` をキャッシュした後に `node1` を別名へ移し、新しい `/A.txt → node2` を作ると、古いキャッシュを使う PUT が node1 を上書きし得ます。

KV は negative lookup もキャッシュし、反映遅延が「必ず60秒以内」とは限りません。

**修正案：**

- パスキャッシュは最終権威にしない。
- mutation 前には現在の親・名前・revision を強整合側で検証。
- `space/tree generation` をキャッシュキーに含める方式などを検討。
- パス解決を深さ分のネットワーク往復にせず、再帰 CTE 等で往復回数を減らす。
- 認可とパス解決のキャッシュを分ける。

---

## M-03. R2 ETag をメタデータ更新の If-Match に流用できない

**対象：§3 `nodes.etag`、§5 PATCH、§7**

R2 内容が同じまま rename／move しても、内容 ETag は変わりません。ディレクトリにはそもそも R2 内容 ETag がありません。

そのため、現在の設計では PATCH 同士の lost update を検知できません。

**修正案：**

- `content_etag` と `metadata_revision` を分離。
- ノード API の ETag は metadata revision に基づく。
- content API の ETag は対象 blob に基づく。
- WebDAV collection の validator と、子追加・削除時の更新方針を定義。
- `If-Match`／`If-None-Match: *` の失敗は412等で明確に返す。

---

## M-04. 「R2 copy」と Workers binding の機能が混同されている

**対象：§1、§5、§7、§13**

R2 の S3 API には `CopyObject`／`UploadPartCopy` がありますが、Workers の `R2Bucket` binding に同等の `copy()` メソッドがあるわけではありません。

参考実装の R2-Explorer も、確認したコピー処理は `get()` → `put()` です。  
[copyObject.ts:47-58](file:///C:/Users/Administrator/repos/R2-Explorer/packages/worker/src/modules/buckets/copyObject.ts)

**修正案：**

v1 の実装方式を明示します。

- binding のストリームコピー。
- S3 API のサーバ側コピー。必要な限定資格情報と署名処理を追加。
- 不変 blob を参照共有する copy-on-write。参照カウント／GC／所有権設計が必要。

いずれも、コピー元の内容世代を固定し、コピー途中の上書きで混ざらないようにしてください。

フォルダ COPY はファイル1個のコピーとは別に、ジョブ化、部分失敗、名前衝突、クォータ、dead properties の引き継ぎを定義する必要があります。共有とロックを無条件にコピーしてはいけません。

---

## M-05. WebDAV Class 1/2 の宣言に必要な意味論が足りない

**対象：§5、§7、§15**

メソッド名の列挙だけでは互換性を判断できません。最低限、以下を仕様化すべきです。

- 空の PROPFIND body、`allprop`、`propname`、指定 property。
- property 単位の `propstat` と404。
- PROPPATCH の文書順処理・全成功または全失敗。
- protected live property を変更させない。
- LOCK refresh、`supportedlock`、`lockdiscovery`。
- 未存在 URL に対する LOCK。
- `If:` の tagged／untagged list、NOT、複数条件。
- COPY／MOVE の Destination の同一ホスト・許可 prefix 検証。
- Overwrite、Depth、collection の末尾 `/`。
- 201／204／207／409／412／423／424／507 の使い分け。
- COPY／MOVE／DELETE の部分失敗。
- XML namespace、mixed content、未知要素の扱い。

**修正案：**

REST の Problem Details と WebDAV の XML エラーは分離し、共通の内部エラーを各プロトコルへ変換します。

XML には body サイズ、深さ、property 数、property 値サイズの上限を設け、DTD／entity 処理を無効化してください。`fast-xml-parser` で dead property を単純に JSON 化して再出力すると、namespace や mixed content を壊す可能性があります。

なお、**exclusive lock のみをサポートすること自体は問題ではありません**。

## M-06. 大容量転送と「デスクトップ同期を WebDAV で代替」の約束が噛み合っていない

**対象：§0、§6、§7、§15、§17-5**

通常の WebDAV クライアントは、このアプリ独自の `/uploads/:id/parts/:n` を使いません。

したがって、Web UI で100 GBを扱えても、Finder／Explorer／通常 WebDAV の rclone で同じサイズをアップロードできるわけではありません。

rclone の Nextcloud chunked upload 対応も、独自 REST multipart API に自動対応するという意味ではありません。

**修正案：**

サポート表を明示します。

| 経路 | v1 の扱い |
|---|---|
| Web UI | 独自 multipart で大容量対応 |
| 通常 WebDAV | 1リクエスト上限まで |
| CLI 大容量アップロード | 専用 API クライアント等が必要 |
| Nextcloud クライアント | WebDAV だけで完全互換とはしない |

§15 の100 GB multipart 試験は、専用 API クライアント／ブラウザ試験に変更するか、Nextcloud chunking 互換を明示的に実装する必要があります。

## M-07. サムネイル Queue に内容世代と outbox がない

**対象：§3、§6、§10、§13**

`{nodeId}` だけのジョブでは、次の競合が起きます。

- 旧内容の生成が遅れて、新内容用サムネイルを上書き。
- 削除・パージ済みノードへ結果を書き戻す。
- DB 確定後の Queue send が失敗し、永遠に pending。
- Queue の重複配信で同じ仕事を繰り返す。

**修正案：**

- `{jobId, nodeId, blobId, variant, generatorVersion}` を送る。
- 派生物キーにも blob 世代と generator version を含める。
- 結果反映時に現在の参照世代を検証。
- DB 確定と同じトランザクションで outbox を作る。
- outbox dispatcher／pending 修復ジョブを用意。
- 各メッセージを個別 ack／retry。
- DLQ の閲覧、再投入、恒久失敗の可視化を用意。

Queues は at-least-once なので、重複排除は任意ではありません。

## M-08. ブラウザ再読込後の再開とハッシュ計算が過度に楽観的

**対象：§6、§9**

サーバにパート表が残っていても、再読込後にブラウザが元ファイルへ再アクセスできるとは限りません。

また、標準 WebCrypto の `SubtleCrypto.digest()` はストリーミング入力をサポートしません。

**修正案：**

- IndexedDB にセッション ID、ファイル fingerprint、パート情報を保存。
- 再読込後は、対応ブラウザでは File System Access API、その他では再選択を要求。
- 再選択ファイルが同一か確認してから再開。
- 大容量ハッシュは Web Worker 内の incremental JS／WASM 実装等を採用。
- クライアント申告 `sha256` とサーバ検証済み checksum を区別。
- 未検証ハッシュを、保存省略・権限をまたぐ重複排除の根拠にしない。
- 24時間期限が「開始から」か「最終進捗から」かを決め、低速回線を考慮。

根拠：[SubtleCrypto.digest()](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/digest)。

## M-09. 日本語 bigram のデータモデル・検索意味論・容量評価が未完成

**対象：§3 FTS、§12、§17-3**

bigram 方針自体は妥当ですが、以下が不足しています。

- `name_bi` を FTS に追加するだけでは、`content='nodes'` の外部コンテンツ表との対応が取れない。
- 1文字検索。
- 半角／全角、ひらがな／カタカナ、英字大小。
- 記号・絵文字・結合文字。
- token の集合一致による誤検出。
- FTS MATCH の検索構文と、単なる名前検索の違い。
- FTS 再構築、migration、同期不良の検出。
- 共有スコープでの検索結果・snippet・件数の漏えい防止。

**修正案：**

- 検索専用正規化値と bigram 値の保存場所を決定。
- FTS 外部コンテンツ方式との整合を取るか、別構成を選ぶ。
- bigram で候補抽出し、必要なら正規化済み文字列で最終照合。
- 1文字検索はスコープと件数を制限した fallback。
- 利用者入力をそのまま FTS 検索言語として解釈しない。
- 名前の保存用 NFC と検索用正規化を分離。
- D1 の `LIKE` pattern 50 bytes 制限も考慮。
- 実データで索引倍率、rename コスト、検索時間を測る。

## M-10. アプリパスワードと人間の共有パスワードに同じ KDF 方針を使う必要はない

**対象：§3、§4.2、§8、§13**

32 byte の CSPRNG secret は十分高エントロピーです。毎回 PBKDF2 100k を実行すると、WebDAV の大量リクエストで CPU 費用が増えます。

一方、人間が指定する共有パスワードにはオフライン推測への耐性が必要です。

また、Workers Rate Limiting binding は **Cloudflare location ごとの、近似的な制御**であり、厳密な全世界共通5回／分ではありません。

**修正案：**

- ランダムなアプリ secret は SHA-256 等の検証用 hash、または server-side key を使う HMAC を検討。
- 人間のパスワードには salt・バージョン付き KDF を使用し、work factor を実測。
- 高コスト検証の前に安価なレート制限。
- per-IP に加えて per-share／per-credential の制御を検討。
- 重要な全体上限は DO 等で補完。
- 比較は timing-safe に行う。
- アプリパスワードに有効期限・端末単位失効・最終使用記録の間引きを追加。

## M-11. Access identity の更新・失効と Service Token のユーザー対応付けが不足

**対象：§3 `users`、§4、§14**

メールアドレスをキーにした単純 upsert は、メール変更や再割り当て時の扱いが曖昧です。

また、Service Token は人間の Google identity と同じではありません。どのユーザー・スペース・scope として操作するかを決める必要があります。

**修正案：**

- issuer＋subject を主 identity とし、email は属性として扱う。
- 既存 email と別 subject の自動紐づけを禁止。
- `users.disabled_at` 等を追加し、Access が通ってもアプリ側で停止できるようにする。
- JWT の署名、許可アルゴリズム、issuer、audience、期限、必要な claim を検証。
- `aud` は配列形式も扱えるライブラリ検証を使う。
- 未知 `kid` 時は JWKS を再取得し、取得失敗時は fail closed。
- Service Token 専用 principal／mapping を用意。
- Bypass した経路で、`CF-Access-Client-Id/Secret` が付いているだけで認証済み扱いにしない。

## M-12. 共有の失効・Cookie・OG メタ・キャッシュの仕様が互いに衝突する

**対象：§1 KV、§5、§8、§10、§11、§13**

以下を決める必要があります。

- パスワード保護共有で、認証前に名前・サイズ・サムネイルを出すのか。
- 回収箱から復元すると、過去の共有リンクが自動復活するのか。
- パスワード変更で、既存 unlock Cookie はいつ失効するか。
- 取り消した共有のサムネイルが1年間ブラウザキャッシュに残ることを許容するか。
- `share_<id>` Cookie を多数発行した場合の cookie 数・header サイズ。
- `/s/*` と `/api/v1/public/*` をまたぐ Cookie の Path。

`private` は「共有キャッシュに置かない」という意味で、**ブラウザへの長期保存を禁止する意味ではありません**。

**修正案：**

- 保護共有の未認証 OG は汎用情報にする。
- 共有復活は既定で行わず、必要なら明示ポリシーにする。
- Cookie に `share_version`、有効期限、鍵 ID を持たせる。
- Cookie の Path、Max-Age、削除、鍵ローテーションを定義。
- 認証依存 JSON／HTML は原則 `no-store`。
- 共有 content／thumb のキャッシュ方針を別定義。
- 既に受信・保存されたデータや、開始済みストリームを完全回収できないことを明示。

## M-13. 未信頼プレビューとクライアント生成サムネイルの信頼境界が不足

**対象：§5、§8、§9、§10、§13**

HTML／JS／SVG を attachment にする方針は良いですが、それだけで Markdown、CSV、PDF、クライアント生成画像を含むプレビュー全体の安全性が決まるわけではありません。

特に `POST /nodes/:id/thumb` に対して、誰が・どの内容世代の・どんな形式をアップロードできるかが未定義です。

**修正案：**

- 生コンテンツとアプリ本体を、可能なら別 origin に分ける。
- Markdown は raw HTML、危険な URL scheme、外部画像等の方針を明示。
- SSR の名前・note・XML property を文脈に応じて escape。
- SVG は `<img>` での挙動だけでなく、直接開いた場合も安全な応答にする。
- thumb upload は対象 node／blob の権限と世代を検証。
- サーバで形式・寸法・サイズを検証し、可能なら再エンコード。
- read-only の利用者が生成した画像を、全利用者共通の正式サムネイルへ無条件反映しない。
- EXIF GPS 等の派生物への残存方針を定める。

## M-14. 保守ジョブの処理量と回収能力が定義されていない

**対象：§3、§6、§11、§13、§14**

500件／時なら最大12,000件／日です。大量削除が続くと回収が追いつきません。「500件」がノードなのか、削除ルートなのか、R2 キーなのかも曖昧です。

`trash_retention_days=0` を毎時 Cron だけで扱うなら「即時」にはなりません。

**修正案：**

- ノード数・blob数・API呼び出し数・実行時間の予算を別に持つ。
- cursor と checkpoint で次の実行へ継続。
- backlog、最古の未処理日時、回収バイト数を監視。
- サムネイル、旧世代、未登録 multipart も回収対象として分類。
- 週次 `SUM(size)` の対象に回収箱・旧世代・予約をどう含むか定義。
- 全 R2 走査を毎時行うのではなく、操作台帳に基づく回収を主とし、全照合を低頻度の修復処理にする。

## M-15. 名前・隠しファイル・仮想 Shared マウントの互換性リスク

**対象：§3、§7、§8、§13**

- 大小区別ありの名前空間は、Windows／macOS 上のクライアントと衝突し得ます。
- `CON` 等を「警告」だけにすると、作成できてもクライアントで扱えない名前が残ります。
- `.DS_Store`／`._*` の保存拒否は、Finder の操作失敗やメタデータ欠落につながり得ます。
- 実フォルダ `Shared` と仮想 `/dav/Shared` の衝突が未定義です。
- `<owner>/<name>` は表示名変更・同名共有で不安定です。

**修正案：**

- portable-name mode と制約を明示。
- 大小のみ変更する rename をテスト。
- `.`、`..`、percent encoding、`\`、二重デコード、Unicode 正規化の順序を固定。
- 仮想マウント用予約名前空間と安定 ID を設計。
- Finder 用 sidecar を保存するか、制限付き互換モードにするかを実機確認。
- 禁止する場合は「Finder 完全互換」とは宣言しない。

## M-16. 監査・ログ・費用・障害対応が運用設計として不足

**対象：§1、§3、§13、§14**

`activity` を append-only にするだけでは、Cloudflare アカウント管理者や DB 書き込み権限を持つ主体に対する改竄防止にはなりません。

また、「ログに token を出さない」はアプリの `console.log` だけの問題ではありません。共有 token が URL に入るため、リクエストログ・例外・トレースにも注意が必要です。

**修正案：**

- 監査の脅威モデルを明記。必要なら別保管・署名・ハッシュ連鎖を検討。
- activity の保持期間と R2 アーカイブを設計。
- token、Cookie、Authorization、共有パスワード、URL のマスキングを実ログで確認。
- CSV エクスポートの formula injection を防ぐ。
- 監視項目：D1容量・遅延、Queue backlog／DLQ、UploadDO異常、R2孤立物、クォータ差分、429／413、画像失敗、CPU費用。
- Workers Paid $5を総運用費と誤解させず、R2・D1・Images・DO・Queues の利用量試算を示す。
- 画像処理用の300秒 CPU設定を、公開APIの全処理で無制限に消費させない設計を検討。

## M-17. テスト計画が正常系中心で、ストレージの障害境界を検証できない

**対象：§15、§16**

現状の Unit／E2E／litmus は良い出発点ですが、最重要なのは以下です。

**追加すべき試験：**

- R2 成功直後、D1 確定直前の停止。
- D1 確定後、応答前の停止と再試行。
- complete／abort／期限切れの競合。
- 同名作成、同一ファイル上書き、相互 MOVE の競合。
- LOCK と REST 書き込みの競合。

| データ所在地・管理者閲覧 | §1、§4、§13 | データ配置の要求、管理者が他人の内容を読めるか、サポート時のアクセス監査。 |
| バックアップ保証 | §13 | RPO／RTO、復旧手順、設定・secret・DO状態を含む復旧範囲、アカウント侵害への備え。 |

**「WebDAV 対応」と「Nextcloud クライアント互換」は分けて説明すべきです。** Nextcloud クライアントは、単純な WebDAV 以外の discovery・capability・chunking 等に依存する場合があります。

# 5. §17「未決事項」への回答

## 17-1. R2 キー＝不透明 ID 方式のトレードオフ

**推奨：採用。ただし、node ID と blob ID を分け、D1 を名前空間の正本とする。**

### 根拠

- rename／move で大量の R2 コピーが不要。
- 深い階層や大きなフォルダ移動に適する。
- 内容世代を不変にすれば、安全な上書き・復旧・コピー最適化へ拡張しやすい。

ただし、以下は受け入れる必要があります。

- R2 バケットを直接 rclone で見ても、論理フォルダ構造にはならない。
- D1 のバックアップは必須。
- 直接バケット書き込みは原則禁止。インポート経路を別に設ける。
- ユーザー向けエクスポートはアプリが論理パスへ変換する。

**不透明キー方式をやめる必要はありません。「D1 は失ってもよい」という説明をやめる必要があります。**

---

## 17-2. WebDAV 認証の既定

**推奨：アプリパスワードを既定。Access Service Token は上級者向けの別構成。**

### 根拠

- Basic over HTTPS は Finder／Explorer を含む一般的 WebDAV クライアントで使いやすい。
- 端末単位の発行・失効・scope をアプリで制御できる。
- Google IdP のブラウザ認証をクライアントへ要求しなくてよい。

Service Token は自動化・rclone等には有用ですが：

- カスタムヘッダ設定が必要。
- Cloudflare 側の発行・更新が必要。
- アプリ内ユーザーへの対応付けが必要。
- 別 Access アプリなら audience も分かれる。
- 同じ経路を Bypass と Service Auth のどちらで運用するか整理が必要。

初版は認証分岐を増やしすぎず、アプリパスワードを堅牢に実装する方がよいです。

---

## 17-3. 日本語 bigram と D1 FTS5 の実サイズ上限

**推奨：名前検索の v1 として妥当。ただし候補抽出方式として使い、実測で上限を決める。**

### 根拠

- 日本語形態素解析器を Worker に載せるより小さく、名前の部分一致に向く。
- unicode61だけより日本語ファイル名の検索品質を上げやすい。
- 保存する名前と検索正規化を分離できる。

注意点：

- bigram の token 数・転置索引は D1 容量と書き込みを増やす。
- 1文字検索は別経路が必要。
- 文字列の並びや重複を検証しないと誤検出が出る。
- FTS 専用の独立した大容量枠を期待してはいけない。

**確認できたハード上限は D1 全体10 GBです。**  
「FTSなら何百万ファイルまで使える」という実効値は、名前長・props・監査量・索引構成次第なので **要確認**です。

受け入れ試験では、10万ノードだけでなく、その上の規模も使って以下を測るべきです。

- DB全体サイズとFTS増分。
- 検索の p95 と rows read。
- rename／delete の更新負荷。
- 日本語の誤検出・取りこぼし。
- FTS rebuild 時間。
- 監査保持期間を含む容量余裕。

---

## 17-4. PDF／動画サムネイルをクライアント生成に頼る方針

**推奨：v1 の best-effort 機能として採用可能。常時生成を保証しない。**

### 根拠

- Worker 内で PDF／動画処理を本格実装するのは CPU・メモリ・codec の制約が重い。
- 既存の pdf.js／ブラウザデコードを使える。
- Cloudflare サービスの範囲を広げずに実装しやすい。

### 条件

- WebDAV から追加されたファイルは、初回 UI 表示までは汎用アイコンでもよい。
- 大きな動画をサムネイルのためだけに全ダウンロードしない。
- ブラウザの codec 非対応を正常系として扱う。
- クライアント生成物を未信頼入力として検証。
- 正式に保存できる利用者と、ローカル表示のみの利用者を分ける。
- `unsupported / not_generated / failed` を区別する。

「すべての PDF／動画に必ずサムネイル」を要求するなら、Cloudflare内でも別の実行基盤・メディアサービスを採用する設計変更が必要です。現在列挙したサービスだけで当然に実現できるとはしない方がよいです。

---

## 17-5. Business 未満で100 GB級ファイルは現実的か

**推奨：Web UI の multipart なら現実的。通常 WebDAV では別問題。**

### 根拠

HTTP ボディ上限は**パートごと**に適用され、ファイル全体が100 GBでも、各リクエストを十分小さくできます。Business は必須ではありません。

90 MiBパートの場合：

- 100 GB：約1,060パート。
- 100 GiB：約1,138パート。

いずれも10,000パート以内です。

### 修正すべき点

- 現在の `size/9000` 式は、このパート数にはならない。
- 最初から90 MiB固定にする必要もない。32〜64 MiB程度を既定にし、回線・再送・クライアント負荷で調整可能にする。
- セッション期限、再読込再開、Access セッション切れ、並行数、R2操作費用を評価。
- v1 の最大ファイルサイズを明文化。
- rclone による検証経路を正す。

将来、S3 presigned upload を使って Worker をデータ転送経路から外す選択肢もあります。ただし、CORS、署名対象キー、パート制約、期限、完了時認可、予約クォータの設計が増えるため、v1 必須ではありません。

---

## 17-6. `download_count` のセマンティクス

**推奨：「ダウンロード回数」ではなく「ダウンロードセッション発行数」と定義する。**

### 根拠

HTTP GET の回数から、人が保存した回数を厳密には判定できません。

- 動画再生は複数 Range を使う。
- ダウンローダーは並列 Range を使う。
- 再試行や通信切断がある。
- 受信済みデータのコピー回数は制御できない。
- Cookieだけでは、対象内容・期限・再利用範囲が曖昧。

### 推奨モデル

1. 共有の状態・パスワード・権限・上限を検証。
2. 原子的に上限を消費し、download ticket を発行。
3. ticket に share ID、share revision、対象 blob／ZIP manifest、期限を紐づける。
4. 同じ ticket による Range／再試行は追加計上しない。
5. 後続リクエストでも共有の取り消し・削除状態を検証。
6. HEAD、304、失敗応答、サムネイル取得は別扱い。
7. 本文プレビューが同じバイトを提供するなら、その扱いを明確にして上限の抜け道を作らない。

フォルダ共有は「1ファイル＝1セッション」か「ZIP一式＝1セッション」かも決めます。

UI には「最大ダウンロードセッション数」「再開可能期限」と表示し、**厳密なコピー回数制限やDRMではない**ことを明確にするのが誠実です。

## 17-7. Access Bypass 設定ミス時、Worker 側チェックで十分か

**推奨：private API の防御として必須であり有効。ただし、それだけで全体のフェイルセーフとは言えない。**

### 十分に機能する条件

- 全 private endpoint が中央の認証 middleware を必ず通る。
- JWT は署名・issuer・audience・期限を検証。
- 必須設定欠落は fail closed。
- アプリ側ユーザー停止・権限確認も行う。
- 別ホストからの到達でも同じチェックが働く。

### 追加で必要な対策

- `workers.dev`、preview URL、想定外 custom domain の公開方針を固定。
- R2 public access／`r2.dev` を無効化し、本体を直接公開しない。
- Static Assets は選択的 `run_worker_first` の対象外では Worker の二重チェックを通らないことを認識。
- 公開 SPA シェルを許容するか、UI 自体も Worker で保護するかを決める。
- 公開共有・WebDAV の認証は、それぞれ Worker 自身で完結している必要がある。
- 未知ルート・ルート境界・URL正規化を検証。
- Bypass traffic は Access の通常のセキュリティ制御・ログに依存できないため、アプリ側で監視。
- Access 設定を IaC 化し、デプロイ後の未認証スモークテストを行う。
- owner bootstrap を公開到達性から独立させる。

# 6. 総評と、実装前に必ず直すべき点

## 進めてよいこと

**Foundation の限定的な技術検証**は進めて構いません。

- モノレポとビルド。
- Cloudflare binding の疎通。
- Access JWT 検証。
- UI シェル。
- D1／DO の状態遷移の試作。
- multipart、ZIP64、Images の境界検証。

ただし、現在のスキーマ・確定手順をそのまま固定して本番データを扱う Files core に進むと、後から根本的な作り直しになりやすいです。

## 最終評価

この設計の中心アイデアである **「D1 の論理ファイルツリー＋R2 の不透明キー」には賛成**です。Cloudflare だけで小〜中規模の個人・チーム向けストレージを構築する方針も現実的です。

ただし、現在はまだ「機能とサービスの組み合わせ」の設計が中心で、**ストレージとして何をいつ確定し、失敗時に何を残し、どう復旧するか**が弱い状態です。

次のレビュー前に、少なくとも以下の四つを設計の中心へ据えることを推奨します。

1. **不変の内容オブジェクトと、原子的なメタデータ参照切り替え。**
2. **認可・ロック・クォータを全プロトコルで共有する mutation 境界。**
3. **削除・復元・GC・バックアップの一貫した状態機械。**
4. **Cloudflare の実制約に沿った、明示的な機能上限と検証条件。**

これらを先に固めれば、UI、共有、WebDAV、サムネイルは比較的独立して実装できます。逆に後回しにすると、完成後にデータモデルと全 API を横断して修正することになります。
