# Client encryption: implemented scope and remaining gates

利用者向けの初回設定と既存ファイルの移行手順は [暗号化ファイルの初回設定](CLIENT_ENCRYPTION_SETUP.md) を参照してください。

The private browser app provides key enrollment and recovery, encrypted upload and exact-ciphertext resume, local preview/download, and administrator reads. The October 4 adversarial review identified missing sender authentication, administrator-key verification, and server enforcement. The current changes add signed version 2 containers, server-pinned account keys, explicit blob markers, and enforcement of `CLIENT_ENCRYPTION_REQUIRED`. Verification and deployment of these changes must be checked against [IMPLEMENTATION_STATUS](IMPLEMENTATION_STATUS.md); earlier version 1 browser/staging results are not verification of this revision. The review acceptance checklist is [here](reviews/encryption-adversarial-20261004.md).

## Goal and boundary

For files uploaded through the encrypted private-browser path, the owner and an administrator with a wrapped key decrypt content on their own devices. The Worker, D1, R2, queues, and server backups receive the opaque ciphertext container for these uploads. The owner vault is kept in browser IndexedDB; the user downloads a separate recovery JSON file. An administrator's public key is imported and pinned from a file exchanged outside the app. Cloudflare Access authenticates an account; it does not unlock a file key. Each recipient needs their own recovery file or an unlocked device.

This protects file bytes and original filenames of those newly encrypted files from passive access to R2, D1, and backups if the client code and pinned recipient public keys are trustworthy. Opaque `.ncf` names still reveal file count; plaintext folder names, hierarchy, ciphertext sizes, account identifiers, usage, and access history remain visible. Cloudflare can refuse service, delete ciphertext, or replay older valid versions. It can also serve modified JavaScript that steals plaintext or keys. Protection against an actively malicious code host requires a separately trusted, verifiable client and independently checked key fingerprints. Browser code hosted by that provider cannot authenticate its own initial delivery.

## Account identity and signed containers

The first public-key registration belongs to the currently authenticated Access account. A short-lived challenge requires both RSA-OAEP decryption and an Ed25519 signature, bound to that account, credential, epoch, and challenge ID. It sends no recovery secret or private key to the Worker. Registration pins the RSA and signing identities; the same API cannot silently replace them. A replay cannot register a different identity. Administrator lookup joins the registry to the current enabled user's `app_admin` role and excludes revoked keys. The browser compares an imported public-key file against this authoritative registry before pinning it. It also keeps the signing-key fingerprint with its local administrator pin.

An independent Ed25519 signing seed is derived with HKDF-SHA-256 from the existing recovery secret and vault salt, with a separate domain containing the account and RSA fingerprint. This preserves existing recovery JSON files without using the RSA decryption key for signatures. The private signing key is imported as nonextractable. The primitives use the [Web Cryptography Ed25519 API](https://w3c.github.io/webcrypto/#ed25519) and [RFC 8410 key encoding](https://www.rfc-editor.org/info/rfc8410/).

New private-browser uploads use `NCFENC2` and a canonical signed header. The signature covers the envelope, **every recipient wrap**, encrypted original name/MIME metadata, owner ID, and signing identity. Verification requires the registered owner's public signing key and expected owner/admin RSA fingerprints. A key supplied inside the container cannot establish trust by itself. Altering a recipient wrap after signing or constructing a container with only the owner's public key cannot pass this check. Each encrypted data chunk is additionally authenticated with AES-GCM.

The Worker checks the signed header at upload creation and checks the actual bounded R2 header, size, ETag, and header hash again at single/multipart completion. It writes the `blob_encryption` marker in the same atomic mutation that commits the file. List/detail responses expose this record. A matching `.ncf` filename, MIME, or client assertion is insufficient to create a marker. Ordinary plaintext with an opaque-looking name remains ordinary plaintext.

The header signature establishes approval of that header by the registered owner. A legitimate recipient who has the DEK can produce AES-GCM ciphertext; this is not a complete-file nonrepudiation scheme against authorized recipients. The server key registry also does not defend against a provider that changes the JavaScript or the registry itself.

## Administrator decryption confirmation

A signed header proves that the owner approved a recipient list; it cannot prove that a malicious owner supplied a usable RSA wrap for the administrator. A new marker therefore starts with administrator confirmation **pending**. After the administrator's browser unwraps the key and authenticates and decrypts the metadata and first data chunk (the authenticated zero-byte chunk for an empty file), it can sign a receipt bound to the owner, blob, header hash, crypto ID, administrator account, and RSA fingerprint. The server verifies the current administrator's registered signing key before recording that receipt. A member cannot confirm on the administrator's behalf. This is a key-access check: it does not verify every ciphertext chunk, whole-file integrity, or a complete backup restore.

This is a record of the administrator's local decryption check, not a substitute for a full backup restore or protection against future key loss. The interface must distinguish pending confirmation from a recorded confirmation. An administrator's intentional false attestation is outside this proof; the server cannot independently decrypt the wrap.

## Encryption envelope (version 1 inside both container versions)

The `FileEnvelope` has `version=1`, a random 128-bit `cryptoId`, plaintext byte count, fixed 4 MiB plaintext chunk size, calculated ciphertext byte count, and 1–32 unique recipient wraps at the format level. The current upload UI wraps for the owner and one pinned administrator key; an app administrator uploading their own file needs only their own key. Members cannot start an encrypted upload without a pinned administrator key. Unknown fields and noncanonical base64url are rejected. Recipients identify RSA-OAEP-3072/SHA-256 public SPKI keys by SHA-256 fingerprint. The client creates a fresh random AES-256-GCM data encryption key (DEK) for **each new upload**. RSA-OAEP's label contains the format, `cryptoId`, and recipient fingerprint. Adding or replacing an administrator for existing files is not implemented; that would require authenticated rewrapping or re-encryption by an authorized device.

Every 4 MiB plaintext chunk is independently encrypted with a fresh random 96-bit IV and a 128-bit GCM tag. Its bytes are `IV || ciphertext || tag`; an empty file has one authenticated zero-byte chunk of 28 bytes. AAD encodes a fixed magic and version, `cryptoId`, total plaintext bytes, chunk index, total chunk count, and exact chunk plaintext length in fixed-width big-endian fields. Decryption rejects changed content, reordered chunks, wrong size, changed identity, and malformed chunk length. A complete-file iterator checks the expected final chunk and total ciphertext length. A partial range intentionally authenticates only the requested chunks; the caller must separately bind the envelope to the intended node/blob revision.

The 4 MiB cryptographic geometry is independent from the current 64 MiB R2 multipart geometry. A one-pass bounded generator encrypts the source `Blob` chunk by chunk and writes the resulting ciphertext to OPFS; upload transport parts can split a cryptographic chunk. An interrupted transport reopens the **same completed ciphertext file** for retry. It does not re-encrypt overlapping byte ranges under the prior DEK. Every `encryptChunk` call generates a fresh IV. The upload manager verifies the persisted file identity and uses its existing bounded retry rules.

`iteratePlainRange` maps plaintext offsets lazily to exact ciphertext chunk offsets; `planPlainRange` materializes only a bounded small window. The Service Worker requests at most 4 MiB of ciphertext per content-origin Range fetch, joins the at-most-4-MiB-plus-tag encrypted chunk, authenticates it, and emits only the requested plaintext slice. A bounded in-memory ciphertext cache avoids downloading the same chunk again for native media probes, seeking, and download. Cache reuse requires a fresh authorized source HEAD with pinned ETag and size, plus the current client/account/expiry checks. No plaintext enters CacheStorage. Native image, audio, and video elements use a random same-origin virtual URL rather than buffering the entire file. The file picker download path streams authenticated plaintext to a local writable file; its fallback buffers only files up to 64 MiB. The calculated ciphertext size must fit the 500 GiB blob limit, so maximum plaintext is slightly smaller; this format bound does not prove a 500 GiB browser transfer. Existing byte/request budgets remain in force, and very large or repeated reads still require performance and budget-window testing. A complete download checks the exact expected byte count and final chunk.

## Self-contained encrypted container

`encryptedContainer.ts` places one opaque file in R2: eight fixed magic bytes (`NCFENC2` and NUL), a four-byte big-endian JSON byte count, at most 16 KiB of canonical UTF-8 JSON, then the exact concatenated AES-GCM chunks. The JSON contains `{version:2,envelope,encryptedMetadata,ownerId,signer,signature}`. The signature has a separate `ncf-container-header-v2` domain. `encryptedMetadata` stores a 96-bit IV and AES-GCM ciphertext for `{name,mime,lastModified}`. Its AAD binds a separate metadata domain, `cryptoId`, plaintext size, and ciphertext size. The uploaded name is `<cryptoId>.ncf`, so the original filename and MIME do not enter D1 or the R2 key. The MIME inside encrypted metadata is a client claim for local display, never a server-side safety verdict or permission to execute HTML.

Old `NCFENC1` files have no sender signature. They are not automatically treated as authenticated encrypted files. An explicit owner approval first verifies the complete local decryption, then signs the exact node ID, blob ID, revision, header hash, crypto ID, and required administrator fingerprint. The server reads the actual R2 header and records the detached attestation without rewriting the ciphertext. The browser verifies this attestation before opening the file. A legacy header alone cannot establish its historical sender. An existing share or another current node referencing the same blob prevents adoption until resolved. The operator's three previously verified files can additionally be compared with their saved plaintext SHA-256 values.

The parser rejects unknown fields, noncanonical JSON/base64url, oversized or incomplete headers, inconsistent chunk geometry, and trailing or missing bytes when a complete local file is opened. For remote reads, `headerEnd + cipherOffset` maps each authenticated chunk to an absolute Range. The browser checks total object size and pinned ETag across the header reads; the Service Worker rechecks the header bytes, source URL, ETag, exact Content-Range and total size before emitting plaintext. Metadata is released only after DEK authentication. `authenticateContainerMetadata` lets the Service Worker verify it with a cloned nonextractable DEK.

A streamed 206 may omit `Content-Length` on real Cloudflare delivery. The page reader and Service Worker accept that absence, reject a conflicting value when present, and still require exact `Content-Range`, pinned ETag/URL, and an independently counted bounded body length. This matches the [Workers Response length behavior](https://developers.cloudflare.com/workers/runtime-apis/response/#set-the-content-length-header); adding a manual length header to a generic stream does not establish its transport length. A regression test covers the absent-header case without changing body bytes or authentication.

`createEncryptedContainer` streams plaintext from the selected `File`, encrypts 4 MiB chunks, and writes only ciphertext to an OPFS staging file. It returns a completed ciphertext `File` that the upload manager sends unchanged. An injectable writer supports unit testing. Aborts and failures discard the temporary ciphertext. When persisted uploads are loaded, cleanup removes only unreferenced OPFS ciphertext files older than 24 hours. Cleanup and encryption hold the same cross-tab lock, so an active writer cannot be removed. Retrying an upload reuses the **completed exact ciphertext File**. The client records its opaque OPFS filename only after completion, validates it on reopen, and deletes it after confirmed upload or cancellation.

## Recipient vault and recovery

The client generates each recipient's RSA key pair for a specific account ID, exports the private PKCS#8 bytes only long enough to encrypt a vault, then imports it again as a **nonextractable** `CryptoKey`. It generates a random 256-bit recovery secret and derives a vault AES-256-GCM key with HKDF-SHA-256 and a fresh 128-bit salt. The vault uses a fresh 96-bit IV and AAD containing the account ID and public-key identity; unlock requires the expected account ID. The vault stays in local IndexedDB. The downloaded recovery JSON contains **both the encrypted vault and the recovery secret**. It is therefore unprotected key material as a file: anyone who obtains that JSON and the ciphertext can unlock the recipient key. It is not an encrypted recovery backup. Store it separately with strong device or offline protection; do not upload it to this service or add it to a server backup. The setup UI requires exporting it and successfully importing it before activating the key. Wrong recovery material fails authentication. Unlock imports a nonextractable private key and verifies it matches the public key with an RSA challenge.

An administrator's login role grants ciphertext access but does not supply the administrator's private key. The member imports the administrator public-key file, checks its fingerprint through another channel, and pins it locally before encrypted upload. A member can restore their own recovery JSON in a fresh browser and read existing files before repinning the administrator public key; only new encrypted writes require that public key. The administrator can select an owner's encrypted file in the dedicated view and decrypt with their own key. Preview and download use distinct audited admin content actions. Adding or replacing an administrator on existing files is not available. Removing an administrator stops future server reads but cannot erase ciphertext or DEKs already copied by that administrator; sensitive files need fresh DEKs and ciphertext after revocation. Loss of all authorized private keys and recovery files means permanent loss of access.

## Current workflow and limits

1. The private browser stages a new signed container in OPFS and uploads its ciphertext bytes unchanged through the single or multipart path, selected by **ciphertext** size. An unlocked registered owner key and, for a member, a verified pinned administrator key are required. The exact header intent is retained with resumable ciphertext. Encrypted overwrite is disabled; a replacement is a new file. The server uses its verified blob marker to enforce the encrypted-file restrictions independently of the UI.
2. The dedicated `/encryption` view reads a ciphertext header through the existing authorized content ticket, validates the original blob's size and ETag, and opens the envelope locally. Its Service Worker keeps nonextractable keys and random virtual URL registrations in memory, binds each to the private client and account, accepts GET/HEAD and one strict Range, and never forwards an unknown virtual URL. Only allowlisted image, audio, video, and PDF MIME types can be served inline; other types download as an attachment with `nosniff` and `no-store`. The UI currently embeds image, audio, and video; PDF is available by download. Decrypted bytes are not written to CacheStorage or a Worker route.
3. The client renews content tickets about every 180 seconds and asks the Service Worker to renew the same virtual URL only after a same-source HEAD confirms size and pinned ETag. A failed renewal closes the view. Logout, account change, key lock, and view close clear or revoke in-memory registrations. A document navigation without a client ID is rejected; download uses a writable file stream from the controlled page.
4. The `/encryption` view can make a **new encrypted copy** of an existing plaintext file up to 128 MiB. For larger files, the user downloads locally and reuploads through the encrypted browser path. The original plaintext node and prior plaintext backups are retained for safety; the user must verify the new encrypted copy before separately deciding how to retire old data. When `CLIENT_ENCRYPTION_REQUIRED=true`, file writers that cannot satisfy the signed-container contract are rejected on the server, including plaintext upload API requests, public uploads, and DAV PUT/lock-null creation. A policy change is checked again before file commit. Automation remains read-only. Folder names and hierarchy remain visible metadata; folder creation does not encrypt them.

5. Encrypted files and folders containing them cannot currently be renamed, moved, copied, shared, or passed to server-side ZIP/media processing. This conservative restriction is checked on the server as well as in the UI where the marker is available. Trash/purge remains governed by the ordinary owner and retention rules. Restoring encrypted trash requires a destination with no active shared ancestor and no active share rooted in the restored members. The server checks authoritative encryption markers on deleted members before admission and again in the atomic publishing batch; asynchronous tree restores repeat the check during processing and final publication. Disabled and expired shares do not block restoration. These restrictions do not rewrite or silently delete old plaintext files.

## Static worker delivery

The real staging Chrome sends its Service Worker script-registration request without Access cookies. An Access-protected script URL therefore redirects to login and cannot be registered, even when an ordinary same-page fetch of that URL returns 200. The worker bootstrap is consequently built as one self-contained static file at the exact `/public-assets/client-media-worker.js` path, under the existing public-assets Access Bypass. The file contains program code only: no user keys, plaintext, account-specific configuration, or private app UI. Its response allows scope `/` and uses `no-store`; unrelated public assets do not receive that scope header. It has no imported private chunks.

Making that static code retrievable does not authenticate a caller. Runtime key registration and decryption still require the authenticated `/api/v1/me` identity, a permitted private-page client ID, a browser-held nonextractable key, and current authorized content tickets with pinned source size/ETag. Public-share clients and unknown virtual URLs are rejected. This delivery path does not introduce a new Access Bypass policy or expose a private API.

## Verification and launch gates

- Browser verification passed for enrollment and recovery import, encrypted upload, owner and administrator decryption, audited administrator preview/download, native media playback/seeking, exact-byte downloads, lock/reload invalidation, and owner reads after removing the pinned administrator public key. Three private AVIF/Opus MP4/AV1+Opus MP4 files totaling 64,932,182 plaintext bytes were encrypted through the browser UI and fully decrypted and hash-checked in the isolated local environment. The real administrator recovery file was subsequently imported locally into an isolated authenticated Chrome context to migrate all three media files in staging; full plaintext hashes and playback/seeking passed. The originals were trashed/purged with explicit approval, while the 35-day R2 GC grace and old backups remain. The two unused member accounts are excluded from the current rollout at the user's request; their enrollment is not a blocker for administrator-only operation.
- Browser verification of interrupted encrypted multipart resume, long-session ticket renewal, cross-tab OPFS cleanup, and large-file memory/budget behavior remains pending. Unit coverage of these mechanisms does not prove those browser scenarios.
- Earlier version 1 staging verification passed for the private-browser gate, public Service Worker bootstrap, registration, unknown virtual URL rejection, and an isolated browser's encrypted AVIF/MP3/AV1+Opus WebM roundtrip (351,797 bytes). A throwaway verification key was used; playback, seeking, full decrypted hashes, and saved bytes passed without a transport-header shim. Only the test fixtures were trashed/purged and that temporary recovery file was deleted. Those results predate signed version 2 and server-enforced write policy; they must not be presented as verification of the new controls.
- Prove a ciphertext backup/restore drill with an independently held recovery JSON for both owner and administrator. A server backup alone cannot restore their keys. Existing plaintext backup generations remain plaintext until separately retired after verification.
- Verify the new marker and policy across API, DAV, public upload, server jobs, and folder ancestry. Record new browser and staging results separately from the prior version 1 results.

## Key revocation and replacement

The registry does not allow replacement through ordinary enrollment. If a key is suspected compromised, stop new writes and disable the affected account; do not delete the old identity and register a new key under it. There is currently no self-service key revocation UI/API or automated rotation procedure. The database records revocation for controlled operator maintenance, but changing that record requires a separately reviewed recovery plan. Current disabled users, demoted administrators, and revoked keys fail active registry checks. Preserve the old public identity, signatures, and recovery material for an offline investigation and recovery.

Automatic key rotation and rewrapping existing files are not implemented. Replacing an administrator requires decrypting and creating new ciphertext with fresh DEKs and the replacement administrator key on a trusted device, then verifying recovery before retiring originals. Login recovery cannot recreate a lost encryption key. Revocation cannot retract plaintext or DEKs already copied by an authorized recipient.

The cryptographic primitives are standard [Web Cryptography](https://www.w3.org/TR/WebCryptoAPI/) operations. AES-GCM IV and AAD requirements are described by [MDN](https://developer.mozilla.org/en-US/docs/Web/API/AesGcmParams); client-side envelope encryption and key lifecycle considerations are covered by [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) and its [key-management guidance](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html).
